# AI 整理与自动记忆

现在可以在任务详情底部的“反馈与自动记忆”提交建议。系统先让已配置的 AI 提炼长期创作偏好，经过校验、去重后自动保存，不需要再逐条点击“留下”。

单机平台升级后，已启用且经 AI 处理的偏好会冻结在新任务的 `goal.memory_preferences` 中，并保留记忆 ID。API 模型选题消费 selection 偏好，写稿消费 script 偏好；规则模式不消费，visual／quality 范围暂未驱动渲染。旧 `memory_context` 保留兼容。输入接通不等于模型一定遵从，停用只影响之后新建的任务；参见 ADR-0013。

## 使用步骤

1. 配置模型，重启 Studio；在“设置 → 自动记忆”查看配置状态。
2. 打开已有任务，在底部反馈框输入建议。例如：“以后口播少用夸张词，保持简洁。这一条的开头再短一点。”
3. 点击“提交反馈”，等待 AI 整理。合适的结果应是长期的口播偏好，而不是把整段反馈或一次性开头修改直接写入记忆。
4. 根据页面返回的信息确认是否新增；进入“记忆”查看提炼内容、原文依据、处理模型与来源任务。
5. 不合适的记忆可以“停用”，之后创建的新任务不再带入。需要恢复时，明确点击“启用”。已有任务的上下文不追溯修改。

系统不会从资讯正文、成片或模型自己的回答中猜测你的偏好；当前自动触发点是你提交的任务反馈，包括 preference、script、selection 等类别。不需要你手工撰写一条整理好的记忆，但仍需要提供反馈。

## 模型配置

复用项目现有 `[llm]` 配置。四项必须齐全：

| 环境变量 | 内容 |
| --- | --- |
| C2VIDEO_LLM_PROVIDER | api |
| C2VIDEO_LLM_API_BASE_URL | 服务商提供的兼容接口基础地址 |
| C2VIDEO_LLM_MODEL | 真实模型 ID |
| C2VIDEO_LLM_API_KEY | 仅在本机填写的模型密钥 |

详细方法见 [模型配置说明](narration-model.md)。不要将密钥发到聊天或写入反馈。`llm.provider=local` 是规则模式，不是本地大模型，因此不会伪造 AI 记忆处理。配置状态只检查字段是否齐全，不等于已经验证模型连通性。

切换 `[llm]` 为 API 也会使原有选题和口播步骤使用同一服务；本次新增的记忆整理会额外调用该服务。反馈与最多 50 条近期已处理或已停用/过期的记忆记录会发送给你配置的模型，可能产生费用。不自动读取其他应用的聊天历史，不使用知乎凭证作为模型密钥。

可在 `c2video.toml` 添加独立配置节：

```toml
[memory]
enabled = true
min_confidence = 0.8
timeout_seconds = 30
```

也可使用 `C2VIDEO_MEMORY_ENABLED`、`C2VIDEO_MEMORY_MIN_CONFIDENCE`、`C2VIDEO_MEMORY_TIMEOUT_SECONDS` 环境变量覆盖。`enabled=false` 只关闭自动记忆提炼，普通反馈仍保存，已有记忆不删除。模型置信度是自评阈值，不是经过校准的事实正确概率。

## 返回结果

| 状态 | 含义 |
| --- | --- |
| stored | 至少一条 AI 处理后的偏好已保存并自动启用 |
| skipped | 没有新偏好、低于阈值、重复，或命中了输入风险检查 |
| unavailable | 未配置可用的 API 模型；只记录反馈 |
| disabled | 自动记忆关闭；只记录反馈 |
| failed | AI 调用、结果校验或记忆存储失败；不回退到原文写入 |

反馈先独立保存，模型失败不会抹掉反馈。对 malformed JSON、额外字段、错误类型、无原文依据、超长内容等输出采用整批拒绝。用户可调整配置或反馈后再次提交；重复提交可能再次调用模型，但完全相同的记忆不会因此重复入库。

CLI 仍可使用：

```bash
.venv/bin/python -m c2video feedback run_替换为真实任务ID \
  --work-dir /绝对路径/与Studio相同的work目录 \
  --comment "以后优先采用官方来源，口播避免夸张用词。"
```

启用访问保护后，提交反馈和修改记忆需操作员会话或 Bearer 密钥；只读角色可以查看但不能修改。

HTTP 入口保持 `POST /api/runs/{run_id}/feedback`，返回 `feedback_id`、兼容字段 `memory_id`、完整 `memory_ids` 和 `memory_processing`。查询使用 `GET /api/memories`，手动停用使用 `POST /api/memories/{memory_id}`，请求体为 `{"status":"rejected"}`。当前处理在该次请求内完成，不是持久后台队列；页面关闭或进程退出可能需要重新提交。

## 失败诊断与兼容模式

格式回退顺序保持为 `json_schema → json_object → 普通 JSON 提示`，仅 HTTP 400／422 才进入下一层，最多三次请求；401／429／5xx、网络错误或超时不会因此额外重试。每次请求分别计入用量看板。400／422 不一定代表供应商不支持该格式，也可能是请求的其他参数有误，因此三层都失败时仍需检查接口配置。

2026-09-17 修复了原兼容回退丢失 Schema 的缺陷：后两层请求都在提示中携带完整格式定义（含嵌套定义），记忆系统提示也明确给出字段说明与有效／空结果示例。依据 [JSON 模式文档](https://api-docs.deepseek.com/zh-cn/guides/json_mode)，JSON 语法有效不等于符合业务字段要求；本地严格校验仍然保留。该文档用于核对协议行为，不表示当前配置地址一定是该供应商的官方端点。

新处理器版本为 `memory-extractor/2`；历史记忆不改写，失败的历史反馈不会自动重放。部署代码后重启 Studio 后端即可生效，不需要重新构建页面。这次只做了离线模拟验证，没有验证真实模型识别质量，也没有发送付费请求。

页面会分别显示模型调用、输出格式／安全校验和数据库失败，不再合并为一条模糊提示。失败时，HTTP 响应中的 `memory_processing.diagnostic` 与 `memory.processing.failed` 运行事件保存相同的安全诊断信息：

| 错误码 | 阶段与排查方向 |
| --- | --- |
| model_http_error | 模型接口报错；`http_status` 保留状态码，检查鉴权、限流或服务状态 |
| model_timeout | 模型调用超时；检查连通性和记忆总等待上限 |
| model_call_failed | 模型调用未完成；检查网络、端点与模型配置 |
| invalid_model_response | HTTP 返回结构不兼容、缺少文本，或输出不是对象／数组 |
| invalid_json | 文本无法解析为 JSON；不自动发起新的纠错请求 |
| schema_invalid | 字段缺失、多余字段、类型或长度不符；查看安全字段路径与错误类型 |
| evidence_mismatch | 引用依据不属于本次反馈；整批拒绝，不保存模型编造的依据 |
| unsafe_output | 输出命中敏感信息或已知指令风险；整批拒绝 |
| memory_read_failed | 读取已有记忆失败；在调用模型前结束，检查数据库 |
| memory_write_failed | AI 整理和校验通过，但写入事务失败；检查数据库与磁盘状态 |
| processing_failed | 其他本地处理错误；使用诊断编号关联日志 |

`diagnostic_id` 可关联服务日志与运行事件，事件中的 `feedback_id` 可定位已保存的反馈。诊断不保存异常原文、堆栈、模型原始回答、提示词、密钥或端点。格式错误最多保留 8 条允许展示的字段路径／错误类型；额外字段名也可能夹带敏感信息，因此会替换为 `*`，不会原样记录。依据 [Pydantic 的错误结构说明](https://docs.pydantic.dev/latest/errors/errors/)，仅去掉输入值不足以保证位置和上下文字段安全，必须额外做允许列表过滤。

供应商请求 HTTP 200 只表示本次模型请求成功，不代表提炼结果已通过记忆校验，因此用量看板可能显示成功请求而记忆仍为失败。确认原因后可手动重新提交反馈，可能产生费用；系统不会为了“写入成功”跳过格式、原文依据、安全或去重检查。

## 处理与安全边界

- AI 只提出内容、类别、依据、简短说明和置信度，不能指定数据库 ID、审批状态、删除动作或执行工具。
- 单条反馈最多 4000 字符，单次最多提炼 3 条，每条记忆正文最多 240 字符；输入与上下文有总长度限制。提炼请求设总等待上限，兼容模型接口内部可能有格式回退请求。
- 校验连续原文依据确实存在于该次反馈；已知提示注入及凭证模式会被拦截。结构校验和模式匹配不保证识别所有恶意输入或语义错误，仍应定期检查并停用错误记忆。
- 存储使用短事务和规范化文本去重，能够阻止并发写入完全相同的偏好；语义重复、冲突交给模型结合近期记录判断，不宣称覆盖全部历史或具备完美冲突解决能力。
- 已停用或过期的完全相同内容不会被自动恢复；需要恢复时由用户显式启用。模型上下文只看有限近期记录，措辞不同的语义等价内容仍有漏检可能。
- 每条新记忆记录反馈 ID、Run ID、输入摘要哈希、处理模型、处理器版本、原文依据与整理说明。不记录隐藏思维过程。
- 历史记忆原样保留，不批量改写。未经 AI 处理的历史待审记忆不能直接批准，可通过原任务重新提交反馈；旧的已批准记录不自动删除或改状态。
- 新增 [用量看板](usage-dashboard.md) 记录模型请求与供应商报告的 Token；费用区分明确返回值和按配置价格估算，不等同于供应商账单。

## 验证方法

`tests/test_memory.py` 使用冻结响应与离线 HTTP 传输测试提炼、自动启用、拒绝无效输出、调用失败、超时、去重、并发写入、历史记录、停用和 CLI/API 一致性，并验证兼容回退后真正写入隔离测试库、诊断脱敏及存储失败分类。`tests/test_llm_structured.py` 检查两层回退完整保留 Schema、不修改调用方消息、最多三次格式尝试、非格式错误不重试及非法响应处理。均不发送真实模型请求。

`studio/src/Memory.test.tsx` 验证提交中的状态、失败提示、未新增时不宣称成功、出处展示与停用操作。构建后还应以浏览器检查真实前后端交互。

模拟响应测试只能证明流程与防护分支按预期执行，不能证明某个真实模型的长期偏好识别质量。上线使用前，建议用少量不含敏感信息的反馈检查真实服务输出。
